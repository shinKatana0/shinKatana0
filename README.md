### What I believe about engineering

- **Measure, then claim.** A README that says "4 h 35 min on this hardware, and here is why" is worth more than one that says "fast". The same rule applies to roadmaps and to people.
- **Process is a product.** The way a team (or a fleet of AI agents) turns intent into merged code is something you design, test and version — not something that just happens.
- **Local-first and safe by default.** Dry-run, journal, undo, nothing leaves the machine unless the user says so. Most trust problems are design problems.
- **Ownership over headcount.** A small team that owns an outcome end-to-end beats a large team that owns a ticket queue.

### What I'm building

**[sorta](https://github.com/shinKatana0/sorta)** — local-first CLI + web app that indexes and sorts a large photo/video collection (tested on 380 GB / 38 k files) by city, person or event. All ML on-device (CLIP, insightface, optional VLM tier), offline geocoding, exact + perceptual dedup, dry-run / journal / undo, Windows installer, EN/RU/JA. Python · ~800 commits · CI + mypy + coverage.

**[briefboard](https://github.com/shinKatana0/briefboard)** — kanban board + CLI that keeps AI coding agents on a strict `backlog → brief → review → merge` workflow, with an orchestrator/worker split and a written protocol as the single source of truth. Zero runtime deps, on npm (`npx briefboard init`). This is the process I actually use to build the rest.

**How these get built.** I run development as an orchestrator over coding agents (Claude Code and others): I own the backlog, write the briefs, review every diff and every measurement, and merge. The agents write a large share of the code and prose. I say this openly because it *is* the point — the interesting engineering in 2026 is in the protocol, the review gates and the honesty of the numbers, and that part is mine.
